# Phase 1 — System Architecture ✅

This was arguably the most important phase.

We decided the project should be completely **generic**.

Instead of:

```text
Sleep
Mood
Exercise
```

the user creates their own prediction problems.

Example:

```text
Should I Accept This Job?
```

or

```text
Will This Project Succeed?
```

We defined four core concepts:

```text
Category
Feature
Observation
ObservationValue
```

which directly map to machine learning concepts.

---

## Categories

A Category represents one supervised learning problem.

Example:

```text
Should I Buy This?
```

It defines:

* target name
* target type

We decided:

✅ Users can edit

* name
* description
* target name

❌ Users cannot edit

* target type

because changing between regression and classification introduces unnecessary complexity for the MVP.

---

## Features

Features are the predictor variables (**X**).

Examples:

```text
Salary
Commute
Remote
```

Supported MVP types:

```text
numeric
boolean
```

Future:

```text
categorical
```

---

## Observations

This was one of our biggest conceptual breakthroughs.

Each Observation represents **one complete supervised learning example**.

```text
X → Y
```

Example:

```text
Salary = 95000
Commute = 20
Remote = Yes

↓

Accepted = Yes
```

This directly mirrors how machine learning datasets are structured.

---

## Observation Values

Rather than storing columns dynamically, we store:

```text
Observation
↓

many ObservationValues
```

Each ObservationValue connects:

```text
Observation
↓

Feature

↓

Value
```

This allows every category to have completely different features.

---

# Phase 2 — Database Layer ✅

We implemented the architecture in SQLAlchemy.

Core tables:

```text
categories
features
observations
observation_values
```

Important decisions:

✅ Foreign keys

✅ Relationships

Observation values stored as:

```text
VARCHAR
```

instead of separate numeric/boolean columns.

Reason:

The ML preprocessing pipeline will convert them later.

This keeps the database simple while still supporting multiple data types.

---

# Phase 3 — REST API (Current)

Goal:

Expose the database through FastAPI.

The API should describe **domain concepts**, not database implementation details.

Example:

Instead of asking clients to manually create:

```text
Observation
ObservationValue
ObservationValue
ObservationValue
```

they simply send:

```json
{
  "category_id": 1,
  "target_value": "Yes",
  "values": [
    ...
  ]
}
```

The backend handles the rest.

This was an important design decision because the API is centered around what the user thinks they're doing ("creating an observation"), not how it's stored.
